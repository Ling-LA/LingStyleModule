# 0.1.3：两个工作线程与当前风格页预加载

基于 0.1.2，仅落实用户选择的两项优化。模型、提示词、上下文预算、网页风格及最终文本均未因提速而改变。

## 执行顺序

以前线程池 core=1、max=2、队列容量 32；第二个线程通常要等队列满才启动。现在 core=max=2、队列容量仍为 32，前两个任务可以立即执行，超载仍拒绝。线程按任务需要创建，创建后不因空闲超时收缩；不增加第三个工作线程。同一会话的 busy 锁持续到 QQ 发送确认/失败，避免同一会话并发生成和乱序提交历史。

自动回复开始且配置有效时，先向网页主线程提交当前风格的预加载，然后进行图片准备和模型生成。网页空闲才创建 WebView；繁忙时跳过预加载，不打断手动转换、预览或自动回复，也不额外创建并发网页。模型生成结束后进入原网页队列：有有效预加载则继续使用，否则按原方式打开页面。

理想空闲场景下，原先「图片/模型耗时 + 页面加载耗时 + 网页转换耗时」中的前两段可以重叠为约 `max(图片/模型耗时, 页面加载耗时)`。两个会话的模型请求也可重叠；网页翻译仍串行，模型和站点服务时间不受本地控制，不能保证每条消息都提速或给出固定百分比。

## 风格与任务隔离

- 预加载只打开页面，不填入消息、不点击翻译。相同账号、配置 revision、风格可共享一个尚未使用的页面；改变任一项即不能复用。
- 最长预留 60 秒；每秒检查失效，使用前再检查。失效/过期/预加载失败会销毁页面；仍有效的任务可冷启动重试加载。真正转换仍沿用包含排队在内的 45 秒上限。
- 页面消耗一次即交给该任务，结束后销毁；后续任务不能读取旧输出。页面生命周期编号独立于转换任务编号，过期页面的错误回调不能结束新任务。
- 所有 DOM 阶段检查准确风格 URL；填入后绑定任务标识，点击和取结果时检查输入归属。保留目标框基线、忙碌状态、有限重试、限额错误及结果长度检查。
- 配置在排队中、转换中或回调到达时变化均取消旧自动回复；运行时发送前还会复查账号、配置、黑名单和当前聊天页免打扰。
- 输出仍由 `ReplyClient.finishStyle` 原样保留，没有第二次模型润色，没有普通文本回退。手动转换和预览继续使用原有接口，不消费自动回复的预加载租约。

## 开销和验证边界

最多同时两个图片/模型任务，可能增加瞬时内存和上游并发；网页最多一个。智能插话最终选择安静或未命中点评概率时，已经预加载的空页保留至过期或下一条同配置任务使用，不点击翻译。

验证命令：`python tools/test-core.py --json-jar <JVM-org.json.jar>`；Android 构建及 lint；`adb shell am instrument -w -e preload true io.github.ling.style.test/io.github.ling.style.DeviceChecks` 使用真实 Android WebView 与合成本地 DOM 验证隔离。`-e warmup true` 则使用四个官方网站及固定合成句子，结果只报告成功、长度和阶段，不向 QQ 联系人发送消息。详细本次结果见仓库根目录 `VALIDATION.md`。

没有改变 400ms 网页轮询间隔，没有缩短上下文或切换模型。本轮不做真实 QQ 流量的前后耗时对比；现有全局诊断时间戳也不应在两条并发任务时相减当作单条延迟。
