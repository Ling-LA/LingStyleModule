# 回复耗时分析：保留当前网页风格

日期：2026-10-15。基线：0.1.1，修复版：0.1.2。

## 已修复的风格丢失与提速

旧链路：接收/排队 → 图片准备（如有）→ 模型生成 → 网页加载和风格转换 → 通用模型再次校对 → QQ 提交/确认。

新链路：接收/排队 → 图片准备（如有）→ 模型生成 → 网页加载和风格转换 → QQ 提交/确认。

`ReplyClient.alignStyle` 原先允许模型把网页结果重新组织成“轻量角色口吻”，且未传入当前风格标识，无法可靠保留所选风格；无 Key/模型时直接返回 `answer.text`，确定丢弃网页转换结果。后者已通过离线最小复现证实。0.1.2 用不联网的 `finishStyle` 原样返回网页文本，只有空白、超长或 silent 状态会被拒绝。

这省去了成功回复的一次串行模型请求及对应线程池等待。普通已缓存能力信息的文本回复，模型生成调用从两次降为一次；网页自身的转换仍照常执行。减少的是这一整段实际耗时，不代表总回复时间减半，也不能把接口 25 秒读取超时当成每次必省 25 秒。没有同条件真机前后计时，本报告不声称具体提速百分比。

## 源码中的耗时来源

| 环节 | 当前行为 | 对速度的影响 |
| --- | --- | --- |
| QQ 接收 | 内核事件优先；后台补查间隔 10 秒，同步调用间隔 30 秒 | 补查间隔仅影响依赖补查的消息，不是每条必等 10 秒 |
| 工作线程 | `ThreadPoolExecutor(1, 2, ..., queue=32)` | 通常只有一个工作线程；队列满后才会增加第二个，图片下载可阻塞其他会话生成 |
| 模型能力 | `/models` 按接口、模型和密钥身份缓存；已列出模型缓存 12 小时 | 首次或缓存过期会增加元数据请求，热路径通常复用 |
| 图片 | 引用查询至多两次，每次等待上限 6 秒；当前图/引用图分别至多 20 秒下载等待 | 网络慢或历史图需下载时增加耗时；这些是等待上限，不是典型耗时 |
| 模型生成 | 连接超时 6 秒，读取超时 25 秒；保留原上下文和图片，输出上限 256 tokens | 模型、网络及历史图片负载决定实际耗时；当前已对已知官方模型关闭思考 |
| 网页 | 每任务新建 WebView、加载当前风格页、提交转换，结束后销毁；每 400ms 轮询 | 页面初始化和加载均在模型回复之后，且网页队列串行；45 秒预算含网页排队 |
| QQ 确认 | 提交后等回调，最多 20 秒，超时不重发 | 提交到确认是独立阶段，不能把全部等待归为模型慢 |

线程池行为依据 [Java ThreadPoolExecutor 文档](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/ThreadPoolExecutor.html)：达到核心线程数后优先排队，队列无法接收任务才扩容。其余数值来自本项目代码，不是性能基准测试结果。

## 建议顺序（除修复外均未实施）

1. **先记录每条任务分阶段耗时。** 使用单调时钟记录排队、图片准备、模型、网页加载、网页转换和 QQ 确认；只记录阶段、风格枚举及耗时，不记录正文、图片、账号或密钥。按纯文本/图片、单会话/多会话、前台/后台分别比较中位数、P95 和失败率。现有全局阶段时间可能被并行任务覆盖，不适合直接相减做精准基准。
2. **将图片/模型工作线程改为两个固定工作线程。** 保留同会话单任务、现有限速和网页串行队列。主要改善多会话排队，通常不会加快空闲时的单条回复；必须验证上下文隔离、取消、同一模型能力查询合并，以及网页排队没有因生产加快而更容易超时。所选网页及其最终输出完全不变。
3. **在模型生成期间预加载当前风格页面。** 当网页引擎空闲时，可把页面加载与模型生成重叠；模型结果出来后仍在原网页填入同一文本并点击原翻译按钮。只保留当前风格的一个预热页面，切换风格/账号/配置立即失效；处理验证码、授权页和渲染器退出；以任务序号、页面地址、输入值和新输出状态共同防止读取上一条结果。优先重叠加载，而不是同时让多个任务操作同一个页面。
4. **仅在翻译进行时适度缩短结果轮询。** 例如把 400ms 调到 200ms，或合并已就绪页面的填入/点击阶段。若完成时间均匀分布，单次完成发现的平均等待理论上约少 100ms；这不是已实测收益。必须保留按钮 loading 状态、旧输出基线、一次点击去重和授权/挑战识别，测量 CPU/耗电后再决定。

保留风格的验收标准是：页面和转换输入仍对应用户当前选择，网页输出逐字交给发送层，风格切换时旧任务取消，不因提速回退普通文本。网页本身是随机生成服务，同一句再次请求的措辞不保证完全相同；这不等于模块切换了风格。现有完整上下文、图片质量和失败处理不作为本轮提速的牺牲项。

## 本次验证边界

离线 HTTPS 桩验证了真实 `ReplyClient` 的请求数量，以及有/无模型、四种风格文本样例、点评、戳一戳、历史提交和失败分支。风格样例是合成的网页返回值，不是四个上游网页的实测结果。AndroidTest 编译及 lint 结果见 `VALIDATION.md`；真实联系人收发与计时未纳入本次测试。
